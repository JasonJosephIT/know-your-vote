## 2. A second, independent blocker: candidate identities are fixture data, not real people

This is a separate finding from the migration gate above, and would block R1 even if 0005
were applied.

Every candidate row is explicitly demo/fixture data:
- All 26 `candidate_id` values follow the pattern `demo-cand-*`.
- Every `candidate.official_site` is `https://example.org/demo/<name>/...` — not a real
  campaign site.
- Every row in the `source` table (which R1's real siblings R2/R3 also write from) has
  `publisher` values literally labeled `"Demo Fixture (Candidate Campaign Site)"`,
  `"Demo Fixture (State Records Office)"`, `"Demo Fixture (Fictional Gazette Fact Desk)"`,
  with URLs at `example.org/demo/...`.

Per my operating rules — *"a search that finds a person with a similar name is NOT a
match — candidate identity must be certain before an item is even considered"* — I
verification-checked one candidate against a real allowlisted-adjacent source before
concluding this applies to all 26, rather than assuming it from the fixture markers alone:

**Spot check: `demo-cand-sutter` / "Hank Sutter", `demo-fl-agriculture` (Commissioner of
Agriculture of Florida).**
```
WebSearch: "Hank Sutter" Florida Commissioner of Agriculture candidate
```
Result: no hit for "Hank Sutter" anywhere in the results. The actual 2026 Florida
Commissioner of Agriculture general-election field, per Ballotpedia/Florida DOE results in
the same search, is Matthew Edward Taylor (R), Chase "Andy" Anderson Romagnano (D), and
Kyle Chaderwick Gibson (NPA) — three different, real people. "Hank Sutter" is not a
near-miss or an alternate spelling of any of them; there is no name overlap at all. This
confirms the fixture-data markers are not just labels — the candidate roster genuinely
does not correspond to real 2026 Florida candidates for this office, and by extension I
have no basis to treat any of the other 25 `demo-cand-*` rows as real people either.

**Consequence:** Even setting the migration gate aside, running 26 candidate-name searches
against allowlisted sources this run would either (a) find nothing, correctly, for names
that don't exist — a valid but uninformative "0" for every candidate — or (b) risk a
coincidental same-name hit on a real, unrelated person, which the identity-certainty rule
requires me to reject as a match. Padding the feed by loosely matching a real article to a
fixture name would be exactly the failure mode Constitution rule #2 and the identity-
certainty rule exist to prevent. I did not run the remaining 25 as full searches for this
reason — running them would not produce genuine information, only a mechanical repetition
of the one negative result already demonstrated to generalize.
