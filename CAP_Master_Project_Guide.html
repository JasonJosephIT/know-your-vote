0. How to Use This Guide

This is the single consolidated reference for the Civic Awareness Project — every part of the project, creation to production, in one document: product scope, the agent pipeline, the MCP tool layer, the data schema, the voter-facing front end, the back-end services, and how they all connect. It synthesizes the six governing documents; it does not replace them. Where this guide and a governing document disagree, the governing document wins, and this guide must be corrected.

Working protocol with Claude: every section has a stable number and anchor (e.g., §8 Front End, §9.2 Services). To start a work session, point at the section: "We're working on §9.1 — the database DDL." Claude treats that section's requirements, inputs, and outputs as the work order, and checks the governing doc it cites before deviating.
Amendment protocol: any global change (schema, thresholds, tool grants, allowlists, prompts, scope, stack) is made in the relevant governing document first, then recorded as a dated row in the Change Log (§12), with the affected guide sections updated. No silent edits.

1. Project Overview

What CAP is: a non-partisan, location-based service delivering highly sourced, neutrally synthesized political candidate briefs to voters via SMS. A voter texts a ZIP code; the system resolves their races and returns a link to a fully sourced, mobile-first web brief.

Core differentiator: verifiable neutrality through a multi-agent AI pipeline that mechanically separates three categories of information — bias must be detected and blocked by the system itself before a brief is published:

CategoryAgentBucket
What they say — the candidate's self-portraitAgent 1 · Profilerstated_position
What they've done — the legislative/financial recordAgent 2 · Recordverifiable_fact
What is true — adjudicated fact-checks on a fixed verdict scaleAgent 3 · Fact-Checkerverifiable_fact + outside_opinion

2. The Constitution (applies to every agent, every session)

Five non-negotiable rules, inherited by all agents and placed at the top of every system prompt:

1. Every claim maps to a Source object or is dropped. No Source → the claim is not written. No exceptions.
2. "Unverifiable" is a valid verdict. Hallucination is not. Never fabricate a fact, a source, or a URL.
3. Never infer motive. Never editorialize. Only describe.
4. Buckets are sacred. stated_position, verifiable_fact, outside_opinion never cross-contaminate. A wrong-bucket write is rejected by the tool wrapper and by a Postgres CHECK, and halts the pipeline.
5. Reach the database and the outside world only through MCP tools. No direct DB writes, no raw HTTP. The wrapper enforces authorization.

Two additional load-bearing distinctions from Schema v1:

Attribution ≠ verification. Claim.attributed ("did the candidate say it") is independent of verification/verdict ("is it true"). A candidate can accurately state a false claim; never conflate the axes.

Silence is recorded, never filled. A candidate with no stance on a spine issue gets a Position with coverage="no_stated_position_found" — measured honestly, never fabricated, never a silent gap.

3. Pipeline — Creation to Production

STAGE 1 INTAKE & RESOLUTION (deterministic) FL DoE candidate file + FEC API → Race + Candidate objects → spine issue set defined & LOGGED │ STAGE 2 AGENT EXECUTION (AI layer — 3 agents IN PARALLEL per candidate) Profiler → stated_position Record → verifiable_fact Fact-Checker → verifiable_fact + outside_opinion (every tool call auto-logged via log_action; wrong bucket / off-allowlist = guard block) │ STAGE 3 BALANCE AUDIT (deterministic, no AI — once per race) 3 GATES + 2 FLAGS → PASS or HALT (HALT = composition & dispatch blocked) │ PASS STAGE 4 COMPOSITION Brief Composer → mobile-first HTML (grouped by issue) SMS Composer → 160-char teaser + link │ STAGE 5 HUMAN REVIEW GATE Project owner reviews HTML + SMS + any raised flags │ approval AND verdict==PASS STAGE 6 DISPATCH & PUBLISH Brief published to static host → sms_dispatch (T12) → Twilio trial → owner's phone only

1Intake & Resolution — deterministic layer

Inputs
  • FL Division of Elections tab-delimited candidate file (via doe_file_intake T1)
  • FEC API — federal candidates in FL-10/15/23/28 (via fec_api_query T2)
  • Voter ZIP code (runtime, via jurisdiction_resolve T4)
Outputs
  • Race and Candidate objects with internal IDs, race mapping, primary logic flags (FL = closed primary)
  • Verified candidate_social_account rows (provenance-chained)
  • The race's spine issue set — fixed, neutrally worded, sourced, logged to action_log
  • ZIP → congressional district + statewide race set

Requirements

  • Filter to statewide races + the 4 target districts; merge + deduplicate DoE/FEC records.
  • Social handles ingested only for qualifying_status='qualified' candidates.
  • A handle is verified only if a candidate-authoritative source points at it (official site link, DoE or FEC filing) with provenance_source_id set. Only verified handles enter Allowlist A. Same provenance bar for every candidate in a race — never a lowered bar.
  • Spine issue selection is an editorial decision: it must be settled, sourced, and logged before agents run.

2Agent Execution — see per-agent cards in §4

All three agents run in parallel per candidate. Each writes only to its authorized bucket(s), only through MCP tools. Cross-contamination is a pipeline failure.

3Balance Audit — deterministic core, no AI

Inputs
  • All Profile objects for the race (via db_read)
  • Thresholds (defaults: word 15%, verifiable_fact 15%, stated_position 15%, fact_check 10%; override for testing only)
Outputs
  • verdict: PASS | HALT with exact per-metric numbers (min, max, variance %, breach)
  • flags[] for human review (never change the verdict)
  • balance_check_passed / flag_reason / flagged_at written to each Profile

Requirements

  • Runs once per race, after all agents finish, before composition.
  • Variance formula, locked for all race sizes: (max − min) / max × 100. Mean/CV rejected — it dilutes the least-scrutinized candidate.
  • outside_opinion claims are counted in no metric.
  • Architecture: one pure core (balance_audit_core.py — no I/O, no AI, injected clock) + two adapters (MCP wrapper T10 for the orchestrator; CLI for humans + CI).
  • On HALT: sms_dispatch unreachable until a human resolves the imbalance (e.g., re-run Agent 3 for the under-scrutinized candidate) and the audit passes.

4Composition

Inputs
  • Claims, Positions, verdicts, and Sources for a PASS-ed race
  • Race key dates (election, registration deadline)
Outputs
  • Brief Composer: mobile-first HTML per §8, grouped by issue — per candidate: 📋 What They Say / 📊 What They've Done / ✅ Fact-Check blocks, each with source links; footer with methodology link + bias-flag form link
  • SMS Composer: ≤160-char teaser + link ("Your Florida voter brief is ready. Races covered: […]. Read it here: [link]")

Requirements

  • The composer caps per-candidate contribution symmetrically, so the word-count gate reflects allocated space, not raw footprint.
  • Every rendered claim shows its verdict (fixed six-value scale) and clickable sources.
  • Header notes Florida is a closed primary state.

5Human Review Gate  ·  6Dispatch & Publish

Inputs
  • Final HTML brief + SMS text
  • Balance-audit verdict + any raised flags (surfaced to reviewer)
Outputs
  • Human approval / rejection
  • On approval AND verdict==PASS: brief published to the static host (§8.4), then sms_dispatch (T12) via Twilio trial to owner phone only

Requirements

  • Dispatch is structurally unreachable while a race is in HALT.
  • Flags alone never block dispatch — they inform the human decision.
  • Phase 1 legal posture: owner's phone only, Twilio trial; no mass registration (TCPA mitigation).

4. Components — Agents & Orchestrator

Agent 1 — The Profiler bucket: stated_position

Objective: faithfully capture how the candidate presents themselves — the self-portrait, in their own framing. Structural guarantee: cannot reach any primary API or independent source, so it is incapable of fact-checking.

Inputs (candidate-controlled only)
  • Campaign website, official bio, issue/policy pages
  • Official social accounts — admitted only via Allowlist A (verified handles)
  • The race's spine issue set (given at run start)
Outputs
  • Claim: bucket="stated_position", attributed=true, verification="single_source", verdict=null, issue_id set, citing ≥1 candidate_self Source
  • Position per spine issue (+ candidate-tier extras); coverage="no_stated_position_found" where the candidate is silent

Tools

web_search T5 (Allowlist A) fetch_source T6 (candidate domains) source_register T7 (candidate_self only) db_read T8 (own bucket) claim_write T9 (stated_position only) DENIED: fec/fl-leg/doe APIs, balance_audit, sms_dispatch, other buckets

Rules & halt conditions

  • Never fact-check, adjudicate, verify, or rate any statement.
  • Attribute everything ("The campaign website states…"). Use "states"/"says", never "claims", unless directly quoting.
  • Never contrast words against record — not this bucket.
  • Halts: any write outside stated_position; any source outside Allowlist A; any truth adjudication.

Agent 2 — The Record Agent bucket: verifiable_fact

Objective: document on-the-record actions independent of messaging. Structural guarantee: "primary sources only" is a hard wall — the agent has no web_search at all; it cannot read a news article even if it wanted to.

Inputs (primary sources only)
  • FL Legislature bill/vote system + official journals (fl_legislature_query T3)
  • FEC campaign finance filings (fec_api_query T2)
  • FL DoE finance filings (doe_file_intake T1)
Outputs
  • Claim: bucket="verifiable_fact", attributed=false (this is the record, not speech), verification="verified", issue_id set where mappable, citing primary_doc Sources
  • Neutral action language: "Voted NAY on SB 123 on 2025-03-04"; "Reported $412,000 in receipts in Q1 2026 per FEC filing"

Tools

fec_api_query T2 fl_legislature_query T3 doe_file_intake T1 (finance) source_register T7 (primary_doc only) db_read T8 (own bucket) claim_write T9 (verifiable_fact only) HARD-DENIED: web_search, fetch_source

Rules & halt conditions

  • No news, opinion, advocacy, or non-primary sources — enforced at the wrapper, not by prompt.
  • Never infer why a candidate acted. State the action and its primary record. Stop.
  • May present stated-vs-did side by side, but must NOT label it hypocrisy, flip-flop, broken promise, or contradiction — the reader concludes.
  • Any action not tied to a primary record is not written.

Agent 3 — The Fact-Checker buckets: verifiable_fact + outside_opinion

Objective: adjudicate the truth of specific, checkable claims using independent primary evidence. The only agent with cross-bucket read — but it can never write to stated_position (cannot rewrite the self-portrait).

Inputs
  • Claims surfaced by Agents 1 & 2 (cross-bucket db_read)
  • Independent evidence via Allowlist B (web_search/fetch_source) + primary APIs in read mode
Outputs
  • Factual verdicts → Claim, bucket="verifiable_fact", verdict set (six-value scale), verification="verified" when ≥2 Tier 1
  • Opinions → Claim, bucket="outside_opinion", unrated (verdict=null; excluded from all balance metrics)
  • Split statements: derived_from links each split claim back to the originating stated_position; issue_id carried over
  • Each check increments fact_checks_performed (Symmetric Scrutiny KPI)

Verdict scale (fixed — six labels only, no deviation)

VerdictMeaning
AccurateSupported by ≥2 independent primary sources
Mostly AccurateMostly supported; minor caveats or imprecision
MixedPartly true, partly false, or highly context-dependent
Mostly InaccurateMostly unsupported; some kernel of truth
InaccurateContradicted by ≥2 independent primary sources
UnverifiableCannot be adjudicated with available evidence — a success, not a failure

Tools

web_search T5 (Allowlist B) fetch_source T6 (allowlisted) fec/fl-leg/doe (read) source_register T7 (any type) db_read T8 (ALL buckets) claim_write T9 (verifiable_fact + outside_opinion) DENIED: stated_position writes, balance_audit, sms_dispatch

Rules & halt conditions

  • ≥2 Tier-1 rule: any verdict other than "Unverifiable" requires at least two independent Tier 1 primary sources. Tier 2 is corroboration only — never sufficient, and never inherit another checker's conclusion.
  • Never rate an opinion or value judgment ("taxes are too high" is not checkable) — route to outside_opinion, unrated.
  • Symmetric scrutiny: fact-checks are tracked per candidate and must be balanced within the race.
  • Every source lean-tagged at registration via Source.lean_tag.

Orchestrator / Synthesis Layer deterministic — NO system prompt

Nature: deterministic controller, no model calls, no LLM prompt — it is control-flow code with a runbook. Inventing a "system prompt" for it is wrong by definition.

Inputs
  • Race/Candidate objects from intake
  • Agent completion states; balance_audit result
  • Human approval at the review gate
Outputs
  • Parallel agent runs per candidate; audit invocation per race
  • Profile audit fields written (balance_check_passed, flag_reason, flagged_at)
  • Composed brief + SMS (on PASS); dispatch (on PASS + approval)

Tools

doe_file_intake T1 jurisdiction_resolve T4 db_read T8 (all) balance_audit T10 sms_dispatch T12 (post human-gate) DENIED: claim_write, web_search, fetch_source, adjudication queries

Hard invariants

  • Never calls claim_write — it composes and dispatches, it does not author claims.
  • Cannot call sms_dispatch for a race whose latest audit returned HALT.
  • Every halt countable via action_log.guard_triggered (Audit Block Rate KPI).
  • Flags alone never HALT — only gate breaches do; flags are surfaced to the reviewer.

Allowlist A — Candidate-controlled (Profiler)

Not a static global list — scoped per candidate, derived from the Candidate object at intake. A URL passes only if its registrable domain matches the candidate's official_site, OR it is a known social platform AND the handle matches that candidate's status='verified' registered handle. Everything else — news, PACs, endorsers, party sites, third parties — is blocked.

Matcher requirements (implemented in allowlist_a_core.py)

  • PSL registrable-domain extraction (injectable; built-in default fails closed on unknown suffixes — production must inject a full PSL extractor).
  • Host→platform folding via social_platform.host_pattern (x.com/twitter.com, facebook/fb.com, instagram, youtube incl. /@, /channel/, /user/, /c/).
  • Tracking-param stripping; shortener denylist; redirects never followed; non-http(s) schemes blocked.
  • Fail closed on empty scope (no official_site, no verified handles → block everything).
  • An official_site that is itself a social platform or shortener never admits by domain match — it must enter via a verified social-account row.
  • Every BLOCK is logged before returning: status='fail', guard_triggered=true, guard_type='allowlist'.

Allowlist B — Independent authoritative (Fact-Checker)

Static, curated, two tiers. Every retrieved source is lean-tagged.

TierRoleDomains
Tier 1Primary evidence — counts toward the ≥2 required for any verdictfec.gov · FL DoE (dos.fl.gov) · flsenate.gov · myfloridahouse.gov · leg.state.fl.us · congress.gov · govinfo.gov · gao.gov · cbo.gov · bls.gov · census.gov · courtlistener.com

Logging Layer (action_log)

Inputs
  • Every tool invocation — all twelve tools, reads included — written by the wrapper before returning
Outputs
  • Append-only Supabase table action_log (INSERT-only role; no UPDATE/DELETE granted to anyone)
  • SQL rollups for the three KPIs: Symmetric Scrutiny (fact-checks per candidate), Audit Block Rate (guard halts by tool), Traceability spot-check (written claim with null source_id = violation)

Record fields

log_id · timestamp · agent_id (profiler|record|factchecker|orchestrator) · tool_called (T1–T12) · race_id · candidate_id · source_url · source_id · bucket_written · claim_id · status (success|fail) · failure_reason · guard_triggered · guard_type ('bucket'|'allowlist'|'denied_tool'|null)

  • bucket_written, claim_id, source_id are null for reads and non-write tools.
  • Early-return rejections (e.g., allowlist blocks) are not exempt from logging.
  • Profile.audit.fact_checks_performed is a cache recomputed from action_log — the log is the independent audit trail proving the published numbers were not hand-tuned.

7. Balance Gates & Flags (Balance Audit v1.1 — the four-metric split)

Rationale: verifiable_fact and fact_checks are the scrutiny the neutrality claim rests on → they gate publication. stated_position is candidate-authored and footprint-driven, and spine-issue silence is real, sourced information → these are flags for a human, never "fixed" by fabricating content for the quiet candidate or trimming the loud one arbitrarily. This is what stops self-portrait size or issue silence from masking or manufacturing a scrutiny imbalance.

MetricKindThresholdOn breach
fact_checks varianceGATE< 10%HALT — dispatch blocked
verifiable_fact_count varianceGATE< 15%HALT — dispatch blocked
word_count varianceGATE< 15%HALT (composer caps contributions symmetrically, so this measures allocated space)
stated_position_count varianceFLAG< 15%flag stated_position_asymmetry — human review, no halt
spine_issues_coveredFLAGany gapflag issue_coverage_asymmetry — human review, no halt
Why the split exists: the old blended claim_count could read 15 vs 15 (0% → PASS) while hiding a 50% record-scrutiny gap. Split, verifiable_fact_count breaches and the pipeline HALTs.

The per-race results are published as the Symmetric Scrutiny Log (transparency mitigation for bias accusations): per candidate — word count, split claim counts, fact-checks performed, spine coverage, variances vs. thresholds, verdict, flags. Reference rendering: CAP_Symmetric_Scrutiny_Log.html.

8. Front End — Voter-Facing Web Brief

Decision (2026-07-01): Phase 1 front end is the mobile-first web brief — exactly what PRD §8 specifies. No native app, no PWA, no client framework. The Brief Composer emits complete, self-contained static HTML; the front end is that output plus two supporting pages. Rationale: zero build chain, smallest possible trust surface, nothing between the audited data and the reader.

8.3 Requirements

Inputs
  • Composed brief data for PASS-ed, human-approved races only (Profiles, Positions, Claims, Sources, verdicts, key dates)
  • Jurisdiction slug from jurisdiction_resolve
Outputs
  • Static, self-contained HTML page per jurisdiction, at a stable public URL
  • That URL is the link embedded by the SMS Composer

Functional requirements

  • Publishes only audited data: a page may render only races whose latest balance audit is PASS and that cleared the human review gate. A HALTed race never reaches the front end.
  • Every claim renders with its bucket context (Say / Done / Fact-Check), verdict badge where applicable, and clickable source links — traceability is visible to the reader, not just the database.
  • Verdict badges use the six fixed labels only, styled consistently (no color-coding that implies party).
  • Candidate blocks are visually identical in structure and symmetrically capped in length (word-count gate, §7).
  • Candidate order within a race is neutral and deterministic (e.g., ballot order or alphabetical — decided once, applied to every race, documented in /methodology).

Non-functional requirements

  • Mobile-first: readable from 320 px wide; briefs open from an SMS on a phone — that is the primary device.
  • Self-contained: inline CSS, no external JS frameworks, no CDN dependencies, no cookies, no third-party trackers or analytics scripts. Page weight target ≤ 200 KB.
  • Accessible: WCAG 2.1 AA — semantic headings, sufficient contrast, verdicts conveyed by text + shape (never color alone).
  • Versioned: each published brief carries a generation timestamp and pipeline version in the footer; republishing creates a new version (prior versions retained for the audit trail).

8.4 Hosting

Decision: static hosting on Vercel (recommended: zero-config static deploys, CDN, immutable deploy URLs for versioning). Acceptable fallback: Supabase Storage public bucket to keep the stack single-vendor. Either way the host serves only files the publish step (§10, Stage 6) uploads — the front end has no server-side logic and no database access.

9. Back End — Services & Database

The back end is five services around one database. Credential rule: agents never hold secrets; only the MCP tool-layer service and the webhook hold keys.

9.1 Database — Supabase (Postgres)

Inputs
  • Writes exclusively from the MCP tool-layer service (T7 source_register, T9 claim_write, T11 log_action, intake upserts, audit-result writes)
Outputs
  • Reads via T8 db_read for agents/orchestrator; read-only queries for the composer and the Symmetric Scrutiny report

Requirements

  • Tables: the ten Schema-v1 objects (§6) + action_log. DDL already specified for candidate_social_account, social_platform, claim_source (Schema v1) and action_log (Logging v1.0 §2); remaining tables need DDL written from the JSON shapes — one migration file per object, kept in the repo.
  • Constraints are the last line of defense: every enum CHECK, PK, FK, and uniqueness rule from Schema v1 §9 is implemented in Postgres — a wrong-bucket write is rejected by the database even if a wrapper bug lets it through.
  • Roles:
    • cap_tool_wrapper — used only by the MCP tool-layer service. INSERT-only on action_log (no UPDATE/DELETE for anyone — the log is immutable); scoped INSERT/UPDATE on content tables.
    • cap_readonly — composer, Scrutiny-report generator, CI checks. SELECT only.
    • No service uses the Supabase service-role key directly except migrations.
  • Traceability invariant: a claim with zero claim_source rows is invalid; the pre-publish check (SELECT for claims missing sources) must return empty before any compose step.
  • Indexes per Schema v1: social reverse-lookup, log (race_id, candidate_id), partial index on guard_triggered.

9.2 Services

S1 · MCP Tool-Layer Service Python 3.10+

The single chokepoint: an MCP server exposing T1–T12, embedding the pure cores already built (allowlist_a_core.py, profiler_guard_core.py, balance_audit_core.py). The only component holding the DB write role and external API keys.

Inputs
  • Tool calls from agents/orchestrator, keyed on agent_id
  • External data: FL DoE file, FEC API, FL Legislature, fetched web pages
Outputs
  • Guarded DB writes (Sources, Claims, Positions, Profiles, audit results)
  • An action_log row for every invocation, written before returning — including early-return rejections

Requirements

  • Enforces the §5 authorization matrix and both allowlists inside the wrapper — prompts are not the enforcement mechanism.
  • Injects a full PSL extractor into allowlist_a_core (the built-in default is a fail-closed US-centric subset).
  • Holds secrets: SUPABASE_DB_URL (cap_tool_wrapper role), FEC_API_KEY, TWILIO_ACCOUNT_SID/TWILIO_AUTH_TOKEN. Secrets never appear in agent context or tool results.
  • Wrong-bucket claim_write → reject + pipeline halt (guard_type='bucket'); off-allowlist URL → block (guard_type='allowlist'); ungranted tool → deny (guard_type='denied_tool').

S2 · Agent Runtime Anthropic API (Claude) via MCP

Inputs
  • Per-agent system prompts (Agent Plan v1.1 — paste-ready)
  • Candidate/race assignment + spine issue set from the orchestrator
Outputs
  • Tool calls to S1 only — Claims, Sources, Positions per each agent's contract (§4)

Requirements

  • Three agent configurations (profiler / record / factchecker), each connected to S1 with its own agent_id — the wrapper, not the prompt, decides what it can do.
  • Agents hold no credentials and receive no raw DB access.
  • Build order: Profiler → Record → Fact-Checker (needs 1 & 2's claims) → Orchestrator.

S3 · Orchestrator deterministic Python — no model calls

Implements the Agent Plan §5 runbook (see §4 card). Runs intake, fans out the three agents per candidate, invokes balance_audit per race, enforces the human gate, triggers publish + dispatch. Its invariants are listed in §4; nothing here overrides them.

S4 · Inbound SMS Webhook Supabase Edge Function (TypeScript/Deno)

Inputs
  • Twilio inbound-SMS webhook POST (voter's ZIP code text)
Outputs
  • TwiML/API reply, ≤160 chars: "Your Florida voter brief is ready. Races covered: […]. Read it here: [link]"
  • Or a graceful miss: unrecognized/out-of-scope ZIP → short "not covered yet" reply listing covered metros

Requirements

  • Validates the Twilio request signature; rejects unsigned calls.
  • ZIP → jurisdiction via the same deterministic mapping as jurisdiction_resolve (T4) — one mapping table, two consumers, no drift.
  • Returns links only to published briefs; a jurisdiction whose races aren't published gets the "not covered yet" reply.
  • Phase 1: Twilio trial constraints apply — replies effectively reach the verified owner phone only. No marketing content, reply STOP handling left to Twilio defaults (TCPA posture, PRD §10).
  • Stores no PII: the voter's phone number is not persisted; the webhook is stateless (log volume/latency only, no numbers).

S5 · CLI Adapters Python — humans + CI

Thin command-line entry points over the same pure cores: run the balance audit for the human review gate and CI, regenerate the published Symmetric Scrutiny Log, and run the traceability spot-check (§9.1). No logic duplicated — adapters only.

10. System Integration — How It All Fits Together

Two independent flows share one database. The production flow builds and publishes briefs (slow, audited, human-gated). The request flow serves voters (fast, deterministic, read-only). They meet only at the published brief URL.

Flow A — Content production (build time)

FL DoE file ─┐ FEC API ─────┤→ S3 Orchestrator → intake → Supabase (Race/Candidate/social accounts) │ │ spine issues defined + logged │ ▼ │ S2 Agents ×3 (parallel per candidate) │ │ every call → S1 Tool Layer → guards + allowlists → Supabase │ ▼ └→ action_log (every call) │ balance_audit (T10) ── HALT ──→ blocked; human resolves; re-run │ │ PASS │ ▼ │ Brief Composer → mobile-first HTML + SMS Composer → 160-char text │ ▼ │ HUMAN REVIEW GATE (owner reviews HTML + SMS + flags) │ │ approve ▼ ▼ publish HTML → Static host (§8.4) → stable /brief/{slug} URL └───────→ sms_dispatch (T12) → owner's phone

Flow B — Voter request (runtime)

Voter texts ZIP → Twilio → S4 Edge Function (signature check, no PII stored) │ ZIP → jurisdiction (same table as T4) ▼ published brief exists? ├─ yes → SMS reply with /brief/{slug} link → voter opens mobile-first brief (§8) └─ no → "not covered yet" reply (covered metros listed)
