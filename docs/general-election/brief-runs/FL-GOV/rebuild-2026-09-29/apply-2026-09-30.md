`brief.sql` is the rebuild from `reingest-2026-09-29/`, with the second commitment gate and the withheld list (`../../withheld-2026-09-30.json`; none of FL-GOV's passages are on it). It holds 28 sources, 52 issues, 213 claims, 80 positions and 8 profiles.

## How it reached the database

The Supabase MCP is the only path to the database, and the file is too big for one call. It was split mechanically, in file order, into 12 standalone batches. Each batch ran as its own transaction.

| Batch | Contents |
| ----- | -------- |
| b00 | **go dark** (`balance_check_passed = false` on all 8 profiles), then the file's deletes of the race's claims, positions and issues; 28 sources (`ON CONFLICT DO NOTHING`); 52 issues |
| b01–b06 | 213 claims (36, 40, 29, 36, 45, 27) |
| b07–b08 | 213 claim-to-source links, resolved by `url_norm` as in the file (143, 70) |
| b09–b10 | 80 positions (76, 4) |
| b11 | 8 profiles (upsert, which replaces `audit`), and the file's own check that every ballot candidate has a profile |

**Why the race went dark first.** On 2026-09-27 the race was `listed` while the brief went in. This time it was `published`, so a reader could otherwise have seen a half-built brief between batches. The page shows a race's brief only when every ballot profile has `audit.balance_check_passed = true`. So b00 set it to `false` in the same transaction as the deletes. The race stayed `published` throughout; `set_race_publication` was not called.

- Dark from **21:45:47 UTC** (b00) to about **21:58:30 UTC** (the audit write-back), about 13 minutes.
- The page and `getRaceBrief` are cached for 3600 s, so readers most likely kept seeing the old brief throughout; see "Live page" below.
