# Accessibility and performance audit of the live site (2026-10-04)

This is the performance and accessibility pass that the launch handoff asks for in section 7 (`launch-handoff-2026-10-04.md`). The earlier checks ran on demo fixtures. This one ran against real content on https://knowyour.vote, between 20:15 and 21:40 UTC on 2026-10-04.

- **What was tested:** production deployment `dpl_FPx9BjpawHcqLB7fPN3E2oEN5zxe`, built from commit `c57e4cb` on `main`. That commit is the base this branch builds on, not the branch's tip. The branch's later commits (for example `6b3e90a`, which already changes the flag link in fix 13) are not live.
- **What was not tested:** this branch (`claude/launch-handoff-completion`) is not live. Its footer, `/terms` page, reminder call to action and methodology rewrite were not audited. Re-run the harness (last section) after they merge. The footer adds a `contentinfo` landmark and more tab stops after the content. The reminder call to action adds a form to the landing page.
- **Read-only.** No source file was changed. Every request to the live site was a GET; the harness aborts any other method (0 were attempted). No form was submitted. The only click was "Decline" on the cookie banner, in a throwaway browser, which writes to localStorage only.

## Bottom line

- **Performance is good.**
  - Mobile Lighthouse scores run from 90 to 96, desktop from 99 to 100.
  - Pages transfer 260 to 322 KB. About 150 KB of that is JavaScript and 79 KB is fonts.
  - CLS is 0 on mobile and 0.002 on desktop.
  - The only metric outside "good" is the simulated mobile LCP, at 2.7 to 3.5 s.
- **Lighthouse accessibility scores are high (96 to 100), but they miss what matters most.** The problems below come from the keyboard and accessibility-tree passes, not from Lighthouse:
  1. **Keyboard focus is hidden.** For a first-time visitor, the fixed cookie banner covers the focused element. At phone width, the fixed bottom nav does too. At 390 px, up to 13 of the first 30 Tab stops on a page are completely hidden.
  2. **The Donate dialog lets focus escape.** It is `aria-modal`, but the third Tab press moves focus into the page behind the overlay.
  3. **/news is wider than the screen on every phone narrower than 423 px.** The Issue `<select>` sizes itself to its longest option.
  4. **There is no skip link.** Every page has 5 nav stops (desktop) or 4 (phone) before the content, plus 3 more while the cookie banner is open.
  5. **The phone top bar is outside every landmark.** It holds Donate and "Set your district", so screen-reader users moving by landmark never reach it.
  6. **Repeated control names.** On `/candidates` there are 106 buttons named "Keep in mind" and 97 links named "Official site", and none of them says which candidate it belongs to.
- **Found in passing (not accessibility, but trust):** on the live site, every published brief's "Flag this brief as biased" link sends mail to `flag@knowyourvote.example`. That is a reserved domain, so the mail can never be delivered. It is live on all 36 published race pages. This branch already points the link at `hello@knowyour.vote`, so it is fixed once the branch merges (fix 13).
- **What already works:**
  - every page has `lang="en"`, a unique title and one `h1`;
  - race pages have a clean heading outline (office, then candidate, issue and bucket);
  - the accessibility tree has no unnamed buttons or links;
  - every text colour pair passes AA, the lowest at 5.58:1;
  - the global `:focus-visible` ring (5.68:1 against the background) shows on every focusable element that is not covered;
  - there are no keyboard traps;
  - every page except /news reflows at 320 px.

## Ranked fix list

Ranked by user impact: blockers for keyboard and screen-reader users come first, then everyone else. File paths are the live (`main`) versions. Each fix also appears, with the exact change, in this run's structured result for the coordinator.

### Accessibility

1. **Focus hidden under the cookie banner and the bottom nav** (WCAG 2.4.11 Focus Not Obscured, AA).
   - **Who is affected:** every first-time keyboard user, on every page.
   - **What happens:** when Tab moves to an element near the bottom of the viewport, Chrome scrolls only until the element is technically in view. It then sits under the fixed cookie banner, or at phone width under the fixed bottom nav.
   - **Worst cases at 390 px:**
     - `/candidates`: 13 of 30 stops hidden. The banner covers 8: the County and Policy area selects, Search, Jose Javier Rodriguez's four stops and the Chief Financial Officer heading. The bottom nav covers 5: the Attorney General heading and Blaise Ingoglia's four stops.
     - `/measures/FL-AM2-general`: 11 of 30 stops hidden.
     - `/races/FL-SEN-general`: 9 of 30 stops hidden.
   - **Fix, in three parts.** Scroll padding alone is not enough, as the simulation below shows.
     - In `src/app/globals.css`, add `scroll-padding-top` and `scroll-padding-bottom` on `html`, sized to the fixed bars. Mobile: top 56 px, bottom 96 px plus the safe-area inset. From `md`: top 88 px, bottom 24 px. Add a `--kyv-overlay-bottom` term to the bottom padding.
     - In `src/components/features/SitePrompts.tsx` (`ConsentBanner`), set `--kyv-overlay-bottom` on `<html>` to the banner's height plus 12 px while it is open (a `ResizeObserver`), and remove it on unmount.
     - In `src/app/layout.tsx`, grow the `<body>`'s bottom padding by the same variable: `pb-[calc(88px+env(safe-area-inset-bottom))]` becomes `pb-[calc(88px+env(safe-area-inset-bottom)+var(--kyv-overlay-bottom,0px))]`, and `md:pb-0` becomes `md:pb-[var(--kyv-overlay-bottom,0px)]`.
       - **Why:** without it, a focusable element near the end of a page cannot scroll clear of the banner, because there is no scroll room below it.
       - **Closed banner:** the variable is unset once the banner is answered, so the padding goes back to today's values.
       - **Where it goes:** the change has to be in the body's Tailwind classes. A rule in the base layer of `globals.css` would lose to them.
       - **Checked:** Tailwind 4.3.2 compiles both classes to the intended `padding-bottom`.
   - **Simulated on the live pages** (`fix1-sim.mjs` in the appendix, GET only):
     - **Method:** the CSS was injected into each page and the variable set to the banner's height plus 12 px. The script walked the first 30 Tab stops and counted those whose focused element was completely covered.
     - **How it compares with the summary table:** this counts covered probe points, not "no visible change on screen", so a few live counts differ slightly from the summary table.

     | Page | 390 px: live / scroll padding only / plus body padding | 1280 px: live / scroll padding only / plus body padding |
     | --- | --- | --- |
     | `/` | 6 / 3 / 0 | 1 / 1 / 0 |
     | `/races/FL-SEN-general` | 9 / 0 / 0 | 4 / 2 / 0 |
     | `/races/FL-GOV-general` | 5 / 0 / 0 | 3 / 0 / 0 |
     | `/races/FL-CFO-general` | 7 / 1 / 0 | 1 / 1 / 0 |
     | `/measures/FL-AM2-general` | 11 / 1 / 0 | 2 / 1 / 0 |
     | `/privacy` | 2 / 2 / 0 | 0 / 0 / 0 |
     | `/candidates` | 13 / 0 / 0 | 0 / 0 / 0 |
     | `/news` | 4 / 0 / 0 | 0 / 0 / 0 |

     - **Scroll padding only:** every stop still covered was one of the last on its page ("How we stay fair", "Flag this brief as biased", "Privacy", "Read the methodology"). Each time, the page was already scrolled to its end.
     - **With the body padding added:** no stop was covered, fully or partly, by the banner or a nav bar on any page, at either width. The only partly covered stop left is the `/news` Issue select running off the right edge at 390 px, which is fix 3.
     - **Side effect:** while the banner is open, the end of each page has extra empty space about the banner's height.
     - `/methodology` was not simulated, because it had no covered stops to begin with.
   - **Verify:** after the change, re-run `a11y-run.mjs` (against a preview deployment, or production after merge). The "hidden focus" column should be 0. Re-run it once `SiteFooter` is live too, because the footer adds stops below the content.
   - **Recommended (pending founder confirmation):** keep the banner fixed and pad around it. The alternative is to move the phone banner into the page flow.
2. **Donate dialog: focus escapes the modal, and is not returned on close** (WCAG 2.4.3 Focus Order; ARIA modal dialog pattern).
   - **Who is affected:** the dialog opens on the next page a visitor views after answering the cookie banner, so almost every visitor sees it once.
   - **What happens, tested live:**
     - Focus starts on Close, then moves to Donate and then to Not now.
     - The next Tab moves to the methodology page's `<summary>`, behind the `bg-black/40` overlay.
     - Escape closes the dialog but leaves focus wherever it was.
   - **File:** `src/components/features/SitePrompts.tsx` (`DonateDialog`).
   - **Fix:** use a native `<dialog>` opened with `showModal()`.
     - The browser then makes the rest of the page inert, keeps focus inside, and turns Escape into a `cancel` event. Call `preventDefault()` and then `onClose()`.
     - Style the backdrop with `backdrop:bg-black/40`.
     - Record `document.activeElement` before opening, and focus it again in the effect cleanup.
     - Drop the window `keydown` listener.
   - **Verify:** no Tab in `dialog.mjs` should print `OUTSIDE dialog`.
     - Every Tab should print `IN dialog`, except one stop where focus leaves for the browser's own controls, printed as `BROWSER`. A native modal dialog does that by design; the page behind stays inert.
     - This was checked offline with a native `<dialog>` in the same Chromium: Close, Donate, Not now, `BROWSER`, then back to Close.
3. **/news overflows on phones** (WCAG 1.4.10 Reflow, AA; affects everyone).
   - **What happens:**
     - The Issue `<select>` is 399 px wide, because a `<select>` sizes itself to its longest option.
     - Its wrapper is a flex item with `min-width: auto`, so `max-w-full` on the select has nothing to bound it.
     - The page is 423 px wide at 320, 360, 390 and 412 px viewports. The "Set your district" chip and the right edge of the cookie banner are cut off.
   - **File:** `src/app/(public)/news/page.tsx`, the two `<div className="flex flex-col gap-1">` wrappers inside the form.
   - **Fix:** add `min-w-0 max-w-full` to both wrappers.
   - **Verify:** `extra-run.mjs` reports `overflow: false` for `/news`.
4. **No skip link** (WCAG 2.4.1 Bypass Blocks).
   - **What happens:** every page has 5 stops (desktop) or 4 (phone) before the content, 8 or 7 while the cookie banner is open. Screen-reader users can jump by landmark (`nav`, `main` exist). Keyboard-only users cannot.
   - **File:** `src/app/layout.tsx`.
   - **Fix:**
     - Add an `<a href="#content">Skip to content</a>` as the first child of `<body>`, styled `sr-only focus:not-sr-only` with a fixed, visible position on focus.
     - Wrap `{children}` in `<div id="content" tabIndex={-1} className="flex flex-1 flex-col focus:outline-none">`, so each page's `main.flex-1` still fills the height.
   - **Note:** another session is editing `layout.tsx` on this branch to add `SiteFooter`. Apply this on top of that change.
5. **Phone top bar is outside every landmark** (axe `region`, on every page at phone width).
   - **What happens:** at phone width, Donate and "Set your district" sit in a fixed `<div>` with no landmark. Screen-reader users who move by landmark never reach the district chip, which is the only place to change or forget a saved district.
   - **File:** `src/components/nav/SectionNav.tsx`.
   - **Fix:** change that `<div className="fixed inset-x-0 top-0 …">` to `<header>` with the same classes. It becomes the `banner` landmark at phone width and stays `display: none` from `md`.
6. **Controls whose names repeat with no candidate in them** (WCAG 2.4.6 and 2.4.4; affects screen-reader users who move through a list of links or buttons).
   - **Counts on `/candidates`:** "Keep in mind" ×106, "Official site" ×97 (97 different sites), "Read their brief" ×82, "About this candidate" ×24.
   - **On FL-GOV:** "Keep in mind" ×8 and "Flag this brief as biased" ×8.
   - **Fix:** add a visually hidden suffix with the candidate's name. The visible text stays the same, so the accessible name still contains the label (WCAG 2.5.3).
     - `src/components/ui/SaveToggle.tsx`: add an optional `name` prop and render `<span className="sr-only">: {name}</span>` after the label. Pass `name` from all four callers: `CandidateBrief.tsx` and `RaceListing.tsx` (`candidate.legal_name`), and `CandidateBrowser.tsx` and `SavedCandidates.tsx` (`c.legal_name`).
     - The same suffix goes on "Official site" in `CandidateBrief.tsx`, `CandidateBrowser.tsx`, `RaceListing.tsx` and `SavedCandidates.tsx`, on "Read their brief" and "About this candidate" in `CandidateBrowser.tsx`, and on "Flag this brief as biased" in `CandidateBrief.tsx`.
     - In `CandidateBrowser.tsx`, the race heading links ("United States Representative" ×16) need the district. Move the district `<span>` inside the `<Link>`.
7. **/news jumps from `h1` to `h3`** (axe and Lighthouse `heading-order`).
   - **What happens:** story cards render `h3` with no `h2` above them. On candidate pages (`CandidateNews.tsx`) and outlet pages, the same card correctly sits under an `h2`.
   - **Fix:**
     - In `src/components/features/NewsStoryCard.tsx`, add `headingLevel?: "h2" | "h3"` (default `"h3"`) and render the title in that element.
     - In `src/components/features/NewsFeed.tsx`, pass `headingLevel="h2"`.
8. **"candidate-added issue" runs into the issue title** in the heading's accessible name.
   - **What happens:** FL-GOV's outline reads "School choice and voucherscandidate-added issue". There is no space between the title and the `<span>`, only a CSS margin.
   - **File:** `src/components/features/IssueSection.tsx`.
   - **Fix:** insert `{" "}` before the `<span>`, and change its `ml-2` to `ml-1` to keep the visual gap.
9. **Small, tightly spaced social links** (WCAG 2.5.8 Target Size, AA).
   - **What happens:** on FL-GOV, four Instagram and Facebook links in the candidate headers are 18 px tall with a 4 px row gap (Lighthouse on both presets; axe at 412 px). The same markup is in `RaceListing.tsx` and `SavedCandidates.tsx`.
   - **Fix:** give these links `inline-flex min-h-[24px] items-center`.
     - Use the arbitrary value: this theme redefines `--spacing-6` as 32 px, so `min-h-6` would be 32 px.
10. **Weak form-control boundaries and suppressed focus rings** (WCAG 1.4.11 Non-text Contrast; 2.4.7).
    - **Borders:** text inputs and selects use `border-border-strong` (`#cfc7b6`), which is 1.68:1 on white. On `/candidates` the search box has only a visually hidden label, so the border is its only outline.
    - **Focus rings:** the selects and the "Show news" button on `/news`, and the selects and search input on `/candidates`, set `focus:outline-none`. Their only focus cue is a 1 px border colour change.

### Performance

Every page already scores 90 or more on mobile, so these are improvements, not blockers.

- **P1. The cookie banner is the LCP element for first-time visitors** on FL-SEN, on FL-CFO (desktop) and on `/candidates`.
  - **Why it matters:** the banner renders only after hydration (`SitePrompts` returns `null` until it has read localStorage). On a slow phone, LCP therefore waits for the JavaScript.
  - **Options:**
    - **Recommended (pending engineering and founder confirmation):** render the banner in the server HTML, and hide it before first paint with a one-line inline script in `<head>`. The script reads `kyv.ads-consent` and sets `data-kyv-consent` on `<html>`, and CSS hides the banner when that attribute is set. `scripts/verify-no-stored-location.ts` checks localStorage keys, so it will need to know about that script.
    - **Cheaper:** shorten the banner's paragraph so it is no longer the largest text block on screen.
- **P2. Fonts are preloaded on every page.** Three woff2 files (79 KB, about 27% of page weight) are preloaded everywhere. In `src/app/layout.tsx`, set `preload: false` on `IBM_Plex_Mono`. It is used for source lines and metadata, below the fold. Keep Inter and Figtree preloaded.
- **P3. The one stylesheet is render-blocking** (8 KB compressed). Lighthouse's render-blocking insight estimates 160 to 310 ms saved on simulated mobile, depending on the page (150 to 300 ms off FCP and LCP). `experimental.inlineCss: true` in `next.config.ts` inlines it (`node_modules/next/dist/docs/01-app/03-api-reference/05-config/01-next-config-js/inlineCss.md`). It is experimental, so try it on a preview deployment and re-run `lh-run2.mjs` before turning it on in production.
- **P4. Some JavaScript is unneeded:** Lighthouse estimates 43 KB of legacy JavaScript and about 28 KB unused in the largest chunk (`1d4ssdcso9zyo.js`, 74 KB compressed). This is mostly framework code; look at it with a bundle analyzer before changing anything.
- **P5. `/` and `/candidates` are rendered per request** because they read the district cookie on the server (deliberate; see the comment in `src/app/(public)/page.tsx`). Reading it on the client, as `DistrictChip` does, would let the landing page be cached at the edge. That is a design trade-off, not a defect.

## Method and limits

- **Tools:**
  - Lighthouse 13.5.0, with the default mobile preset (simulated: 150 ms RTT, 1.6 Mbps, 4x CPU slowdown) and the desktop preset;
  - axe-core 4.13.0;
  - Playwright 1.56.1 driving Chromium 141.0.7390.37, headless;
  - all installed in a scratch directory, not in the repo.
- **How pages were fetched:**
  - In this sandbox, Chromium cannot complete TLS through the egress proxy. Rather than change any trust settings, the browser makes no network requests of its own: every request is paused and fetched by Node, which verifies TLS against the session's CA bundle, and the response is handed back.
  - Only GET and HEAD are forwarded.
  - On a normal machine none of this is needed (see "Repeat the run").
- **Correcting transfer sizes:**
  - The browser receives decoded bodies, so Lighthouse would simulate downloading the uncompressed bytes. For example, FL-GOV's HTML is 524 KB decoded and 35 KB as served (brotli).
  - A first pass that left this uncorrected scored FL-GOV mobile at 68 and is discarded.
  - The reported pass saves Lighthouse's artifacts, replaces each request's transfer size in the DevTools log with the compressed size measured on the wire, and re-runs the audits.
- **TTFB is not modelled:** responses come from the harness's cache. See the note under the summary table.
- **Visitor state:**
  - Every run is a first-time visitor: cookie banner open, no district cookie, no consent.
  - The Google Ads tag therefore never loaded, and no analytics loaded because `NEXT_PUBLIC_PLAUSIBLE_DOMAIN` is unset in production. Third-party weight after "Accept" was not measured.
- **What was not run:**
  - No real screen reader (VoiceOver, NVDA, TalkBack). The screen-reader findings come from Chromium's accessibility tree; a person should still do a short pass (founder action).
  - Not checked: `/candidates/[id]` pages, the `?view=races` ballot view, the issue-filtered race view (`/races/[id]/issues`), 200% text zoom, and Windows high-contrast mode.
- **Reliability:**
  - Something else in the sandbox intermittently killed Chromium's child processes (exit code 9) during the first batch. The runners now launch a fresh browser per page and retry.
  - Every reported a11y run completed on its first or a later attempt.
  - One Lighthouse run did not complete cleanly: the batch's `/news` mobile pass hit `PROTOCOL_TIMEOUT` in the CSSUsage gatherer ("Method: CSS.enable").
    - The runner does not retry on a Lighthouse runtime error, so that run was kept, with its unused-CSS audit missing.
    - A DevTools timeout suggests CPU contention, which also inflates TBT.
    - The `/news` row therefore uses two later runs of that page on its own, with the same script, on a quiet machine (load average 0.25 when they started). Both completed with no runtime error and agreed within 2 ms of TBT.
    - The other 17 Lighthouse runs reported no runtime error.
- **PageSpeed Insights:** it was tried for a real-network cross-check and refused (anonymous daily quota exhausted).

// v2 of the request handler: same rules as intercept.mjs (GET/HEAD only,
// everything else aborted; retries for the flaky egress tunnel; in-memory
// cache), but it fetches the raw compressed bytes with node:https, decodes
// them locally for Chromium, and records the real over-the-wire size of each
// URL so the Lighthouse devtools log can be corrected before audit mode.
//
// Run Node with NODE_USE_ENV_PROXY=1 so node:https tunnels via HTTPS_PROXY.

import https from "node:https";
import http from "node:http";
import zlib from "node:zlib";

const cache = new Map();
export const sizes = new Map(); // url -> { headerBytes, bodyBytes, decodedBytes, encoding }
export const log = { hits: 0, misses: 0, blocked: [], failed: [], retries: 0 };

const FORWARD = [
  "accept", "accept-language", "user-agent", "rsc", "next-router-state-tree",
  "next-router-prefetch", "next-router-segment-prefetch", "next-url", "range",
  "cookie", "referer",
];
const DROP_RESPONSE = new Set([
  "content-encoding", "content-length", "transfer-encoding", "connection",
  "keep-alive", "alt-svc", "strict-transport-security",
]);

function keyFor(method, url, headers) {
  const h = Object.fromEntries(Object.entries(headers).map(([k, v]) => [k.toLowerCase(), v]));
  return [method, url, h["rsc"] ?? "", h["next-router-prefetch"] ?? "",
    h["next-router-segment-prefetch"] ?? "",
    (h["accept"] ?? "").includes("text/html") ? "html" : ""].join("|");
}

function rawGet(method, url, headers) {
  return new Promise((resolve, reject) => {
    const mod = url.startsWith("https:") ? https : http;
    const req = mod.request(url, { method, headers }, (res) => {
      const chunks = [];
      res.on("data", (d) => chunks.push(d));
      res.on("end", () => resolve({ res, body: Buffer.concat(chunks) }));
      res.on("error", reject);
    });
    req.on("error", reject);
    req.setTimeout(30000, () => req.destroy(new Error("timeout")));
    req.end();
  });
}

function decode(body, enc) {
  if (!enc || enc === "identity") return body;
  if (enc === "br") return zlib.brotliDecompressSync(body);
  if (enc === "gzip" || enc === "x-gzip") return zlib.gunzipSync(body);
  if (enc === "deflate") return zlib.inflateSync(body);
  if (enc === "zstd" && zlib.zstdDecompressSync) return zlib.zstdDecompressSync(body);
  throw new Error("unsupported encoding " + enc);
}

async function fetchLive(method, url, headers) {
  const h = {};
  for (const [k, v] of Object.entries(headers)) if (FORWARD.includes(k.toLowerCase())) h[k] = v;
  h["accept-encoding"] = "br, gzip";
  let lastErr;
  for (let attempt = 0; attempt < 6; attempt++) {
    try {
      const { res, body } = await rawGet(method, url, h);
      const enc = res.headers["content-encoding"];
      const decoded = decode(body, enc);
      const outHeaders = {};
      let headerBytes = `HTTP/1.1 ${res.statusCode} ${res.statusMessage}\r\n`.length + 2;
      for (let i = 0; i < res.rawHeaders.length; i += 2) {
        const k = res.rawHeaders[i].toLowerCase();
        const v = res.rawHeaders[i + 1];
        headerBytes += k.length + v.length + 4;
        if (DROP_RESPONSE.has(k)) continue;
        outHeaders[k] = outHeaders[k] ? outHeaders[k] + (k === "set-cookie" ? "\n" : ", ") + v : v;
      }
      sizes.set(url, { headerBytes, bodyBytes: body.length, decodedBytes: decoded.length, encoding: enc ?? null });
      return { status: res.statusCode, headers: outHeaders, body: decoded };
    } catch (e) {
      lastErr = e;
      log.retries++;
      await new Promise((r) => setTimeout(r, 400 * (attempt + 1)));
    }
  }
  throw lastErr;
}

export async function serve(method, url, headers) {
  if (method !== "GET" && method !== "HEAD") {
    log.blocked.push(`${method} ${url}`);
    return null;
  }
  if (!/^https?:/.test(url)) return null;
  const key = keyFor(method, url, headers);
  if (cache.has(key)) { log.hits++; return cache.get(key); }
  log.misses++;
  try {
    const r = await fetchLive(method, url, headers);
    if (r.status < 500) cache.set(key, r);
    return r;
  } catch (e) {
    log.failed.push(`${url} ${e?.code ?? e?.message}`);
    return null;
  }
}

// Usage: NODE_USE_ENV_PROXY=1 node lh-run2.mjs <outDir> <path> [<path> ...]
//
// 1. Warm-up load (fills the cache through intercept2, recording each URL's
//    real compressed size).
// 2. Lighthouse gather mode -> artifacts + devtoolslog.json on disk.
// 3. Patch devtoolslog.json: each request's encodedDataLength becomes the
//    measured header + compressed body bytes, and content-encoding is put
//    back on the response headers. Without this, Lantern simulates the
//    download of decoded bodies (FL-GOV HTML: 524 KB decoded vs 35 KB br).
// 4. Lighthouse audit mode on the patched artifacts -> report.
// Default simulated throttling in both presets; nothing else is changed.

import path from "node:path";
import puppeteer from "puppeteer-core";
import lighthouse from "lighthouse";
import desktopConfig from "lighthouse/core/config/desktop-config.js";

fs.mkdirSync(outDir, { recursive: true });

async function attach(page) {
  await page.setRequestInterception(true);
  page.on("request", async (req) => {
    if (req.isInterceptResolutionHandled()) return;
    const r = await serve(req.method(), req.url(), req.headers());
    if (!r) return req.abort("blockedbyclient").catch(() => {});
    req.respond({ status: r.status, headers: r.headers, body: r.body }).catch(() => {});
  });
}

function patchDevtoolsLog(file) {
  const events = JSON.parse(fs.readFileSync(file, "utf8"));
  const urlById = new Map();
  for (const e of events) {
    if (e.method === "Network.requestWillBeSent") urlById.set(e.params.requestId, e.params.request.url);
  }
  let patched = 0;
  let unknown = 0;
  for (const e of events) {
    const id = e.params?.requestId;
    if (!id) continue;
    const s = sizes.get(urlById.get(id));
    if (e.method === "Network.responseReceived") {
      if (!s) { unknown++; continue; }
      e.params.response.encodedDataLength = s.headerBytes;
      if (s.encoding) e.params.response.headers["content-encoding"] = s.encoding;
      patched++;
    } else if (e.method === "Network.dataReceived" && s) {
      const ratio = s.decodedBytes ? s.bodyBytes / s.decodedBytes : 1;
      e.params.encodedDataLength = Math.round(e.params.dataLength * ratio);
    } else if (e.method === "Network.loadingFinished" && s) {
      e.params.encodedDataLength = s.headerBytes + s.bodyBytes;
    }
  }
  fs.writeFileSync(file, JSON.stringify(events));
  return { patched, unknown };
}

  });

const summary = [];

      console.error("attempt", attempt, "threw", p, preset, e.message);
      return false;
    });
    await browser.close().catch(() => {});
    if (ok) break;
   }
  }
}

    const artifactsDir = path.join(outDir, "artifacts", slug);
